Tier Model

HAIWAVE ships as three layered packages. Each layer builds only on the ones to its left, so you can take a lower layer without the ones above it — the SDK does not pull in the reference agent. Use the layer that fits your work. This section only defines the vocabulary; the capabilities are enumerated in §5 (for B and C) and §10 (for A).

// build order — strictly acyclic (enforced by tsc -b project references)
@haiwave/protocol  →  @haiwave/client-sdk  →  @haiwave/reference-agent  →  root app
   (wire types)        (prescribed surface)      (reference scaffold)         (composition)
1.1The Three Tiers

Tier 0 — Wire And Transport. The protocol message schemas (@haiwave/protocol) plus transport and auth: the outbound client (HaiWaveClient, TokenManager), the MCP (Model Context Protocol) server, JWT (JSON Web Token) validation, and the PROTO-3 callback HMAC (Hash-based Message Authentication Code). You cannot change Tier 0 without leaving the network.

Tier 1 — Prescribed Conformance. The interfaces and invariants every agent must honor: the chat pipeline phases, the intent taxonomy, the grant floor, the write-confirmation gate, the transaction-touching chains, the data-disclosure contracts. Extend at the declared extension points; never remove or bypass them.

Tier 2 — Reference Scaffold. Everything in @haiwave/reference-agent: the reference data layer (a single-file DuckDB by default), the Claude and Gemini adapters, the local embedding model, the reference pricing, lead-time, and recommendation logic, and the UI. Each piece is freely replaceable behind the Tier 1 interfaces.

Data store is your choice. DuckDB is only the quick-start default — single-file and in-process, so the reference agent runs with no external database. Production deployments point the DataStore interface at the data platform they already run (Snowflake or any other) and reuse that investment; the agent is not tied to DuckDB. The heavy native dependencies (DuckDB, embeddings, the LLM vendor SDKs, document parsers) live only in @haiwave/reference-agent — the root app and @haiwave/client-sdk stay free of them, and guard tests pin that boundary.

SDK Quick-Start

The minimum to get a Tier 0 + Tier 1 conformant agent running from @haiwave/client-sdk.

2.1Prerequisites
  • Node.js 22+.
  • A reasoning key. An Anthropic key (ANTHROPIC_API_KEY) or a Gemini key (GEMINI_API_KEY).
  • Network credentials from §3: PARTICIPANT_ID, AGENT_ID, KEYCLOAK_CLIENT_ID, KEYCLOAK_CLIENT_SECRET.
  • @haiwave/client-sdk. Obtained inside the Free Agent source downloaded from the HAIWAVE console (a workspace package consumed from that source, not a public npm install). It declares @haiwave/protocol as a peer dependency, satisfied by the protocol copy that ships hoisted in the same source package (§11).
2.2Tier 0 — Transport And Auth

The SDK provides the transport primitives. Wire them in this order:

  1. Token management. Instantiate TokenManager with your Keycloak client credentials and KEYCLOAK_TOKEN_ENDPOINT. It handles client-credentials token acquisition, caching, and refresh.
  2. Central client. Instantiate HaiWaveClient (typed by the IHaiWaveClient contract) with the TokenManager and HAICORE_BASE_URL. This is your outbound channel to HAIWAVE Central; it attaches the bearer token to every call.
  3. MCP server. Build your inbound MCP server with createMcpServer; per-request session state comes from createSessionState.
  4. Inbound auth. Gate the /mcp route with validateJwt (configured by McpAuthConfig). Enforcement is controlled by MCP_AUTH_REQUIRED; supply KEYCLOAK_JWKS_URI / KEYCLOAK_ISSUER for RS256 in production.
  5. Origin assertion. Call assertHaiCoreOrigin on inbound requests so only HAIWAVE Central can route to your agent (§6.7).
  6. Register tools and resources on the MCP server (the protocol tool surface is in §10.2).

import { TokenManager, HaiWaveClient, createMcpServer }
  from '@haiwave/client-sdk';

// Outbound: client-credentials token manager + the authenticated Central client.
const tokenManager = new TokenManager({

const central = new HaiWaveClient({
  baseUrl, participantId, agentId, forwardOnBehalfOf: false,
}, tokenManager);
// `central` now attaches a fresh bearer token to every haiCore call.

// Inbound: the MCP server haiCore calls into. Register the tools you expose (§10.2).
const { mcpServer, sessionState } = createMcpServer({
  serverInfo, capabilities, registrations,
});
// Mount mcpServer on a Streamable HTTP transport at POST /mcp — see src/mcp/server.ts.
2.3Tier 1 — Chat Baseline

If your agent exposes the conversational surface, wire the prescribed chat baseline from @haiwave/client-sdk:

  1. Pipeline. Run each turn through runMessageTurn, which executes the eight prescribed phases in order (§10.6).
  2. Sessions. Manage conversational state with SessionManager / ChatSession.
  3. Routing. Route against the VALID_INTENTS taxonomy using QueryRouter (with an IQueryFastPath for the regex fast path).
  4. Grant floor. Enforce grant gating via hasGrant; the quote_accept intent requires quote_owner_outbound (§10.6).
  5. Chains. Register the 13 prescribed transaction-touching chains in the PromptChainRegistry.
  6. Write gate. Preserve the pending-confirmation state machine (handlePendingConfirmation plus the arming in finalizeTurn) so no write executes without explicit acknowledgment.

2.4 Deploy-as-is shortcut (C). If you are not modifying code, skip §2 and go to §4. The SDK quick-start is for Journeys B and A; chain extension points belong to §5.4 (B) and §10 (A).

Network Registration

Joining the HAIWAVE network is a gated, human-reviewed process, not a self-service signup. Every participant is screened and explicitly admitted by a HAIWAVE gatekeeper before any credentials are issued. Credentials — and therefore the ability to download the agent and operate in network mode — arrive only on approval. The flow has three stages.

  1. Public application. A prospective supplier completes the form on the marketing site (/join). This creates an inert holding-pen record (status = pending_approval); no participant, Keycloak user, or session is created yet, and the response is a uniform acknowledgement that leaks no screening outcome. It collects contact, legal entity name and website, headquarters country (an ISO 3166-1 alpha-2 code — the screening key), headquarters address, and at least one business identifier (Tax ID or DUNS, the Data Universal Numbering System ID).
  2. Automated jurisdiction screening. HAIWAVE Central assigns a risk tier from the headquarters country alone — blocked (sanctioned jurisdiction), elevated (outside the gatekeeper's domestic jurisdiction), or standard (domestic). Screening is a signal for the human gatekeeper, not an automatic gate.
  3. Gatekeeper adjudication. A gatekeeper reviews pending applications at Admin › Registration requests (/account/admin/registrations) and approves or rejects (both audited). Rejection requires a reason and tombstones the record (PII partly redacted) for later re-invitation. Approving a blocked-tier application requires an explicit, audited override.

On approval. An idempotent provisioning step creates your participant record (participant_id / agent_id), creates a Keycloak user for console access (a one-time setup requiring password reset plus TOTP, a Time-based One-Time Password, enrollment), and emails a single-use activation link. From there you can sign in to the console, download the agent source or Docker image, retrieve your agent's Keycloak client credentials, and proceed with the network-mode deployment in §4. The six trust tiers assigned to your counterparties are covered in §6.2.

Outbound now, inbound after endpoint registration. Once it has valid credentials, your agent authenticates and makes outbound calls (discovery queries, orders, catalog and manifest exchange) as soon as it boots. For HAIWAVE Central to route requests to your agent (discovery, incoming quote requests and orders), your agent's public endpoint (AGENT_PUBLIC_URL) must be registered with Central. Today that registration is performed by HAIWAVE from the address you provide; until it is in place, your agent is reachable outbound but is not yet discoverable or orderable by counterparties.

PlannedSelf-service endpoint registration. A console control to register and update your agent's callback endpoint yourself is intended but not yet wired; today the endpoint is registered by HAIWAVE as part of onboarding.

Deploy the Reference Agent
4.1Source And Image

After §3 approval, download the reference agent from the HAIWAVE console download page (Account › Agent Software) — the definitive source for the Free Agent client source package, the @haiwave/client-sdk, and this configuration guide. The reference image is a standard node:22 build. The container ships its config as a seed template and mounts the runtime config on a volume (VOLUME /data/config). On first boot the entrypoint copies the seed into the mounted volume and never overwrites existing files, so an image upgrade cannot clobber your runtime customizations. Set CONFIG_DIR=/data/config to point the agent at the mounted volume.

PlannedFIPS-hardened agent image. A FIPS-hardened agent image is on the roadmap. The FIPS-validated images that exist today are for HAIWAVE Central, not the partner-deployed agent.

4.2Standalone vs. Network Mode
  • Standalone. A local AI assistant for your team. No HAIWAVE credentials, no network participation, no Go Fish, no manifest exchange.
  • Network. Everything standalone does, plus Keycloak authentication, network registration, Go Fish discovery, manifest exchange, and order flow; Central observes your agent's availability through this normal traffic. Requires PARTICIPANT_ID, AGENT_ID, and Keycloak client credentials.

PlannedAutomatic mode selection. The intended design selects the mode from the presence of network credentials. Today the switch is not wired: the chat surfaces assume network mode, and PARTICIPANT_ID / AGENT_ID carry placeholder defaults when unset. Treat the reference agent as network-oriented; coordinate with your HAIWAVE contact for a pure standalone deployment.

4.3aAvailability: Observed, Not Probed

Earlier editions described heartbeats as governing availability while nothing on the platform side drove them. v1.66 closed that gap by probing every registered endpoint on a five-minute sweep and jailing an agent that stopped answering. The v1.75 platform removed that machine rather than tuning it: HAIWAVE Central no longer sends heartbeats and no longer jails an agent for silence. It derives your agent's availability at read time from two facts it already holds, the last time your agent itself called Central (its own polls, registration, and any authenticated inbound call) and whether Central's recent dispatches to your agent succeeded. The result is one of four values, shown on your console dashboard and on the agent listing (§6.11).

AvailabilityMeaning
healthyRecent traffic in either direction.
quietNo traffic for a while (four hours by default). Nothing is wrong yet; the agent is screened on its next contact.
unreachableRecent dispatches to the agent are failing. The dashboard says so, by agent name.
not deployedNo endpoint has been registered for the agent yet (§3).

Two consequences follow, and both are worth designing for rather than discovering:

  • An unreachable agent misses work. A quote request, order, or discovery query that Central cannot deliver is recorded as a failed dispatch. Quote requests and orders are re-sent once the agent is answering again, with less content than the original (§7.5), unless the buyer's request has expired or been withdrawn in the meantime; a discovery query is not re-sent, and the buyer's result simply does not include you. There is no penalty state to leave and nothing to re-enrol: the agent returns to service automatically on its next successful exchange.
  • A direct query does not silently drop you. A buyer who queries your agent by name while it is unreachable is told that the agent is unreachable, in a fixed message with no detail, rather than getting nothing back. Being unreachable is visible to counterparties as unreachability, not as absence. Availability does not currently remove you from discovery results or rank you lower; only an administrative suspension of your account does that.

The heartbeat_hello MCP tool (§10.2) is retained for wire compatibility and is no longer called by Central. The practical requirement is the one §A.1 states: the process must stay up and stay reachable at AGENT_PUBLIC_URL. An agent that sleeps, scales to zero, or is stopped overnight is shown to its own operators as unreachable until it answers again.

4.3bUpgrades

Non-destructive by construction: build the new package, stop the old container, start the new one with the same volumes. Configuration is seed-once, so your edits survive, and the database migrates itself forward. Verify with /health; the reported version should match the new package. The package's UPGRADING.md and CHANGELOG.md carry per-release notes. Agent releases jump from 1.50.0 to 1.56.0 and from 1.60.0 to 1.65.0, and the tag sequence also skips v1.64.0 and v1.66.0, whose releases are carried inside the following tag; a gap is deliberate, not a failed download.

Upgrading to 1.65. A price with no currency is withheld instead of being sent out under an assumed USD; read §7.1a before upgrading.

Upgrading to 1.66 and 1.67. Four changes are visible from outside the agent. None requires configuration, and all four are corrections rather than new options:

  • Quote expiry is two windows, not one (§7.1c). Check any integration that computes an expiry.
  • The quote status a buyer receives is derived differently (§7.1d). A draft whose lines are all partly filled now reports partial where it previously reported unable.
  • Availability is visible (§4.3a). An agent that is not running is shown to its operators as unreachable rather than as merely stale, and it misses work while it is down.
  • A catalog query with no search term is refused (§10.6) instead of returning an arbitrary slice of the catalog.

4.4aNative-Quote Configuration

Seven variables govern the seller's own quoting loop (§7.7) and the document it produces (§5.6). Three of them have no flat default: they derive from AGENT_INTERACTION_MODE, because a policy that waits for a person is only honorable on a deployment where a person exists.

VariableDefaultPurpose
QUOTE_RESPONSE_MODEderivedHow the agent answers an inbound quote request. auto_respond prices it and puts the draft straight back on the wire; queue files it as a work item (§6.10) and the buyer receives the protocol's asynchronous pending acknowledgment. Unset derives: agent_and_human gives queue, agent_only gives auto_respond.
NATIVE_QUOTE_RELEASE_MODEderivedWhether the agent side may release one of your own quotes (§7.7) without a person. auto releases it; queue files a native_quote_release work item and nothing is released until someone approves it. Unset derives by the same rule: agent_and_human gives queue, agent_only gives auto. Your own console buttons are a person acting directly and are never queued.
NATIVE_QUOTE_COMMIT_MODEderivedThe same agent-side door for committing a quoted order into your ERP. auto commits; queue files a native_quote_commit work item. Same derivation, same boot refusal.
NATIVE_QUOTE_CUSTOMER_PRICINGaskWhether the agent reads a customer's own ERP price lists for a draft (§7.7). ask waits to be asked from the draft's review screen; auto fetches before a quote is generated; off is a legal value that refuses the pricing door at request time, with an authored refusal naming this setting rather than an ERP error, not at boot. Independent of AGENT_INTERACTION_MODE.
NATIVE_QUOTE_VALIDITY_DAYS30How many days a generated quote's price stands for. The expiry is printed on the customer's document, so the value must be a whole number of days of at least 1.
DOCUMENT_RENDERERcentralWhich document renderer produces the quote PDF (§5.6). central is the only value this release ships; substitute your own the way an ERP connector is substituted.

An absent file is legal and is not a boot refusal: it logs a warning, and every generated quote renders its seller block absent rather than inventing a value. A file that is present but unreadable, not valid JSON, or schema-invalid does refuse the boot.

These variables need an ERP connector to matter. ERP_CONNECTOR is unset by default, which means no connector, and the customer lookup and customer-pricing doors then refuse with a message naming exactly that rather than doing anything (§7.7, §5.5). Setting the variables above changes nothing on a deployment with no ERP configured.

4.4bConfiguration The Agent Refuses To Start On

Environment validation reads the native-quote settings of §4.4a inside the same fail-fast step as the rest of the configuration, before anything listens, so a value the agent cannot honor stops the boot with a message naming the variable instead of being accepted and quietly ignored. Five refusals:

  • An unrecognized NATIVE_QUOTE_RELEASE_MODE or NATIVE_QUOTE_COMMIT_MODE. The valid values are auto and queue.
  • queue on either of those two while AGENT_INTERACTION_MODE=agent_only. A headless agent has no human surface, so no one could ever approve the queued action, and the boot says so rather than deadlocking quietly.
  • A NATIVE_QUOTE_VALIDITY_DAYS that is not a whole number of days of at least 1. A fraction, a zero, or a number with a unit written after it is refused rather than rounded, because the value is printed as a date on a customer's quote.
  • An unrecognized DOCUMENT_RENDERER. central is the only value this release ships (§5.6).
  • An unrecognized NATIVE_QUOTE_CUSTOMER_PRICING. The valid values are auto, ask and off.

QUOTE_RESPONSE_MODE, which governs the same question for an inbound quote request, obeys the identical two rules: an unrecognized value is refused, and queue on an agent_only agent is refused.

Both resolved policies are logged on every boot, including whether the value was derived rather than set, so the posture an agent actually runs under can be read from its log instead of inferred from its environment.

Why a refusal rather than a fallback. Each of these settings decides whether a commercial action happens without a person. A misspelling that landed silently on a default would answer that question without telling anybody, which is the one outcome an operator cannot audit after the fact.

5.2LLM Provider And Cost

The agent uses a hosted LLM for all reasoning; you pay the provider directly (HAIWAVE neither provides keys nor proxies calls). Select the reasoning provider with LLM_PROVIDER (claude default, or gemini) and the embedding provider with EMBEDDING_PROVIDER (local default — in-process and key-free — or gemini). Default models are claude-sonnet-4-6 and gemini-2.5-flash. Both adapters are supported configurations.

Cost is driven by query volume and catalog size. An Epicor Kinetic connector ships with the reference agent. Once selected it reads only. Turning the write path on is a deliberate, documented step rather than a setting: the package ships docs/erp-write-enable.md, the runbook for a session in which a person watches the first booking against a live Kinetic test company before the write path is trusted anywhere. The connector is mapping-driven. Endpoints, authentication headers, composite-key types, field maps and price-per divisors are supplied as data in a mapping file you mount, not as code. Before first use. The connector has not yet been exercised against a live Kinetic instance, so every assumption it makes about your installation comes from published API definitions rather than from observation. 6.8Approval Gateway

Optional, disabled by default. The approval gateway pauses a high-stakes action until an explicit decision comes back, instead of letting the agent act on its own. It gates three action types — trading_pair_connection, invoice_approval, and order_release (the last only when the order value exceeds APPROVAL_GATEWAY__ORDER_RELEASE_THRESHOLD). With the gateway off (APPROVAL_GATEWAY__ENABLED=false, the default), these actions proceed without gating.

  • Native. The agent holds the pending approval in-process — pair it with a local approval UI or a simple hold-and-resume. This is the mode when no MCP endpoint is set.
  • MCP. The agent delegates the decision to an external gateway at APPROVAL_GATEWAY__MCP_ENDPOINT. The decision returns asynchronously to POST /approvals/callback, whose body is verified with an HMAC (Hash-based Message Authentication Code) over the raw request bytes using APPROVAL_GATEWAY__CALLBACK_SECRET — the PROTO-3 guard the SDK exposes as verifyCallbackSignature.

While a request is pending the originating action is staged and resumes on the decision. A pending approval not decided within APPROVAL_GATEWAY__EXPIRY_MINUTES (default 1440 — 24 hours) is swept (every __EXPIRY_CHECK_INTERVAL_MINUTES, default 5) and resumed as rejected; the gateway polls decision status every __POLL_INTERVAL_SECONDS (default 180).

Currency, for anyone implementing a pricing engine. The protocol no longer supplies a default currency, so your engine must return the currency alongside the price or return neither. A price with the currency field absent is not a partially-populated result the platform will complete for you: it is a price that will be withheld from publication (§7.1a). If your engine cannot denominate a product, say so explicitly rather than emitting a bare number.

The contract is Tier 1: IApprovalGateway (submit/poll), IApprovalRepository, and one IApprovalResumeHandler per approval type — all in @haiwave/client-sdk. The reference agent supplies the concretes (NativeApprovalGateway / McpApprovalGateway, ApprovalRepository, and the trading-pair / invoice / order-release resume handlers); swap any behind those interfaces.

6.9Query Guard

Managed Access (§6.1) decides whether a counterparty may ask you something. The query guard decides how much any one of them may ask over time. It exists for a specific abuse: a counterparty legitimately entitled to query you, using that entitlement to map your catalog, your pricing curve or your inventory position by asking many small permitted questions.

Configured entirely in the console; there is no agent-side setting. Four rule types, each settable globally and overridable per trust class: sku_repeat (the same SKU queried repeatedly), sku_breadth (how much of your catalog one counterparty touches), ad_hoc_cap (volume of one-off queries) and excess_volume (query volume out of proportion to that counterparty's actual order history). Precedence is trust class, then global, then platform default, resolved independently per rule type. Shipped defaults are alert-only: out of the box the guard reports what it sees and changes nothing about what your agent answers.

A trip is silent. When a rule pauses a counterparty or elevates their logging, the decline they receive is byte-identical to an ordinary access-posture decline. They cannot tell the difference, so they cannot discover your thresholds by probing for the boundary. Only the block action notifies them, deliberately: blocking is a relationship decision you want known.

It fails open. A guard defect or database outage must never become an outage for the counterparties you do want to serve. If the guard cannot evaluate, your agent answers normally. A missed detection is recoverable; a self-inflicted denial of service to your own trading partners is not.

It layers under the platform limit. HAIWAVE enforces a per-responder hourly probe ceiling that nobody can configure. The query guard sits beneath it, where you decide what is reasonable for your business. It cannot raise the platform ceiling.

Caveat. excess_volume is evaluated at your agent, after the response, because the order truth it compares against lives with you rather than at Central. An agent on a protocol older than 3.51 silently does not enforce it, and the console marks the rule accordingly.

The agent does not execute commercial decisions on its own. It surfaces them, and a person acts. The work queue is where that happens, and it lives in your agent's own interface, not in the HAIWAVE console.

Where the default comes from. The container is agent_and_human, so it has a human surface, and every policy that can wait for a person defaults to waiting: an inbound request queues, and so does a release or a commit that the agent side asks for. A headless agent (agent_only) has no console and no login, so the same policies default to acting unattended, and asking it to queue is refused at boot rather than accepted, because no one could ever drain that queue (§4.4b). The chat assistant can report on the queue, and for an inbound quote request committing is done in the queue rather than by asking for it. Your own console buttons are a different thing again: they call the action directly, because a person pressing Generate or Commit is the human validation, and are never queued.

Grants bound what you can take, not only what you can commit (v1.67). The queue offers a Request backlog control that pulls a batch of open items into your working set and holds them for the duration of a lease. That claim is filtered by the same grant reach that governs acting on an item: it hands you only item types you could actually action, because a claim is exclusive and a review-only user checking out a batch used to block, for the whole lease, everyone who could have acted on it. Reading and commenting never required a claim; the queue's All view shows every item and accepts a recommendation without one. The working set is capped (QUEUE_BACKLOG_SIZE, default 10), so a claim is bounded in size as well as in time.

7.1aA Price With No Currency Does Not Publish

Read before upgrading to v1.65. This changes what your catalog publishes. A price is only meaningful alongside the currency it is denominated in. Earlier releases supplied USD as a default wherever a currency was missing, so a partly configured row still went to the network carrying a denomination nobody had chosen. From v1.65 the platform does not invent one: where a currency is absent, the price is withheld rather than published with a guess.

The rule applies uniformly across every outbound surface. Catalog publication sends price and currency together or neither, so a priced row with no currency publishes as an unpriced row; it stays discoverable, it simply carries no price. Discovery withholds an offering the agent cannot denominate rather than returning it with an assumed currency. Quotes require a currency on both lines and totals, and a quote whose lines span two currencies is refused, because a total across mixed denominations has no meaning; a quote the agent is unable to price states your configured currency beside zero totals so the reply stays legible. ERP-sourced prices arriving without a currency are skipped rather than stamped with a default.

The unit price goes with it. A line dropped for having no currency reports no unit price either. This was corrected in v1.66 after a walk of the live console found the earlier behaviour: the quantity and the total were zeroed but the unit price survived, and at that point the surviving figure could be an internal fallback under a borrowed currency, which is exactly the fabricated number the rule exists to keep off the wire.

What to do before you upgrade. Confirm your pricing manifest declares a currency and that priced rows in your catalog carry one. Rows that do not will publish without prices after the upgrade. That is intended, and recoverable at any time by setting the currency, but it is better known in advance than discovered as a gap. The agent applies a one-time migration on first boot which removes the old default from the pricing store: prices already stored keep the currency they have, and nothing is rewritten or deleted.

Where currency belongs. Currency attaches to the price and to the legal entity that transacts, never to a physical site. A facility makes and holds goods; it does not denominate them. If you operate in more than one currency, express that with a pricing manifest scoped to the relevant location (§7.1b), the direct analogue of a currency-denominated price list in an ERP. Do not expect to set a currency on a plant or warehouse record.

7.1cQuote Validity: Two Windows, Not One

A quote's expiry is governed by two independent windows. Conflating them will leave you wrong about one of them.

The request window is how long an open quote request stays live before HAIWAVE Central expires it. When a request omits valid_for_hours, Central defaults to 240 hours (10 days). This is the number that governs how long a buyer can leave a request outstanding.

The price hold is how long the price a vendor quotes back actually stands, counted from when the vendor responds, not from when the request was opened. When the inbound request omits valid_for_hours, the vendor's agent applies its own default of 48 hours. A request that sat open for a week before the vendor answered still only holds that vendor's price for 48 hours past the answer.

These defaults belong to different sides of the exchange, and nothing keeps them in sync unless the field is set explicitly.

An explicit valid_for_hours on the request overrides both. Set it on the outgoing request and it carries through untouched: Central uses it as the request window, and the vendor's quote reports the same figure as its price hold.

A solicitation (§7.5) always supplies its own value, calculated from the solicitation's deadline, so neither default applies there. A ten-day solicitation stays open for the full ten days regardless of what a plain quote request would otherwise default to.

7.1dThe Quote Status A Buyer Receives

A quote carries a per-line status for every line and one envelope status for the quote as a whole. The envelope status is derived from the lines, and v1.67 corrects how: the rule asks whether each line was priced, not whether it was filled completely.

LinesEnvelope status
Every line quoted in fullcomplete
At least one line quoted in full or partly filledpartial
No line priced at allunable

The change is the middle row. A partly filled line, one where you can supply some of the requested quantity but not all of it, previously did not count toward the roll-up, so a draft in which every line was partly filled reported unable. unable is presented to the person releasing the quote as "no line on this request could be quoted", so approving it sends the buyer a refusal, the same answer as denying it. Nothing else changes: no field is added, no new value enters the vocabulary, and the per-line statuses and quantities are exactly what they were. If you parse the envelope status rather than the lines, this is the one change in v1.67 that can affect your integration. Quotes drafted before the upgrade keep the status they were stored with.

7.5Solicitations: Being Invited To Quote

A solicitation is a buyer asking several vendors to quote the same requirement. The mechanism that matters to you is the invite: it substitutes for the trading-relationship gate that would normally have to exist before that buyer could reach you. Being invited makes you reachable for that one solicitation and nothing more. It creates no standing relationship and does not outlive the solicitation.

When an invite arrives, your agent files an actionable item in its work queue (§6.10). From there a person can quote it, or decline it. Declining is a first-class outcome rather than an absence: a buyer receiving four quotes and one decline knows where they stand, whereas a buyer receiving four quotes and silence cannot tell whether the fifth vendor is slow, uninterested, or never received the request.

Two things about pricing here. Your configured price floor is re-read at the moment of use, not captured when the solicitation arrived, so a floor you change while a solicitation is open applies to the quote you send. And quotes are two-tier: the reply records the basis it was priced on, so a quote derived from a list price and one derived from a negotiated or ERP-resolved price stay distinguishable downstream instead of arriving as indistinguishable numbers.

Requires configuration. Quote delivery needs a registered quote endpoint and the paired webhook secret. Self-registration deliberately does not transmit the secret, so an endpoint can be registered and active while still refusing delivery. A 503 means the secret is unset on your side; a 401 means it does not match. Confirm delivery end to end before relying on solicitations, because an undelivered invite is counted as sent.

Declining requires release 1.66 or later. Decline shipped in 1.64 and did not work: the call that carried it announced a JSON body and then sent none, which the receiving service rejected outright, so a decline armed in the console, confirmed, and then failed. It is fixed from 1.66. On 1.64 or 1.65, treat decline as unavailable until you upgrade, because the buyer will read your decline as silence, which is precisely the outcome the feature exists to prevent.

On delivery failures. From v1.66 a delivery attempt that does not land is recorded on the HAIWAVE side rather than passing without trace, so a persistently misconfigured endpoint is diagnosable instead of merely quiet. On the current platform an undelivered quote request is marked as queued for replay, the buyer sees that status rather than a plain pending one, and Central re-sends the request once your agent is answering again (the redelivery note below says what a re-sent request carries). Time lost while unreachable is not given back: the buyer's request window (§7.1c) runs from the original request, and a request that expires or is withdrawn before your agent returns is not re-sent. Confirm delivery end to end anyway; the operator-side record remains the reliable account of whether a quote request reached you.

A redelivery carries less than the original — by design. If Central could not reach your agent, it re-sends the work once your agent is back. A re-delivered quote request arrives without per-line ship-to addresses, and a re-built order arrives without ship-to, notes, or payment details (the purchase-order number is recovered from the backing quote and included). This is not data loss in transit: Central deliberately keeps no durable copy of that content, so a redelivery cannot include it. Do not reject or error a redelivery for the missing fields — treat what it carries as authoritative, and expect the omitted details on the normal exchanges that follow.

7.6Order Collaboration

An order does not always survive first contact with reality. Order collaboration is the channel for changing one after it exists without cancelling and re-placing it: a party proposes a change, the other responds, and the order carries the outcome.

The division of responsibility determines what HAIWAVE can and cannot see. Central holds the lifecycle only, meaning the states a proposal passes through and the fact that it was proposed, accepted or closed. The promises and envelopes stay at the agents, so the commercial substance of what was offered and agreed never leaves your side. The roll-up a counterparty sees is state, not content.

Proposal events are append-only. A proposal is superseded or closed, never edited and never deleted, so the sequence of what was proposed and when stays reconstructible. That is what makes a disputed change auditable rather than a matter of recollection.

Per-line ship-to is supported: different lines on one order can go to different delivery points. A ship-to is stripped before anything is written centrally. It identifies a specific delivery point for a specific deal, which is exactly the kind of detail that should not accumulate in a shared system, so it stays with the transacting parties.

7.7Native Quotes

Everything in §7.5 is about being asked to quote by someone on the network. This section is the other direction: quoting your own catalog to your own ERP customers, who need not be HAIWAVE participants at all. The output is a quote document you send and, when the customer's purchase order comes back, an order booked in your ERP. New in v1.76.

It is off until an ERP is configured. The customer lookup and the customer-pricing door read your ERP through the connector boundary of §5.5, and ERP_CONNECTOR is unset by default. With no connector both doors refuse with a message naming exactly that, so a deployment that has not configured an ERP sees no change from this release.

The loop. Compose a quote from your own catalog, naming lines and quantities. Deliver it to an ERP customer, which is the point at which the customer is confirmed and the header is defaulted from their customer master (terms, currency, ship-to). Optionally read that customer's own price lists and record, per line, what they would be charged beside what the draft says (NATIVE_QUOTE_CUSTOMER_PRICING, §4.4a). Generate the document, which mints the quote's reference, stamps its expiry, and produces the PDF. Then wait for the customer's purchase order, attach it, and commit, which books the order into your ERP.

Stages. A quote is a draft that moves through named stages, visible on the agent's Order Entry tab. A composed quote starts at composing, reaches review once it has been delivered to a customer and enriched, becomes quoted when the document is generated, and then moves committing, committed and verdict_received as the ERP write is made and confirmed. Revising a quoted draft returns it to review and increments its revision number. The stage vocabulary has eleven members in total; the four this list does not name (uploaded, extracted, aligned, resolved) belong to the document-driven purchase-order entry flow that shares the same drafts, and commit_indeterminate is where a draft rests when an ERP write neither clearly succeeded nor clearly failed.

Three doors, one core. The same service answers all of them, so what a quote can do is the same at each door. What differs is only whether the agent side may act unattended.

  • The agent's own console. HTTP routes behind the Order Entry tab. Every route requires quote_owner_inbound, so a user holding only reviewer is refused by the routes themselves rather than shown a read-only screen.
  • Chat. The eleven gestures of §7.8, gated on the same grant.
  • Network MCP. Deferred by decision, not by omission. See the Planned note in §7.8.

The grant floor is quote_owner_inbound at every door, and owner covers it (§6.10).

8.2aReadiness Watchers

A readiness watcher asks a forward-looking question per SKU rather than reporting a trailing signal: can each counterparty supply this quantity within this many days? You configure it by attaching a per-SKU ask to the watcher scope, giving a quantity and a window in days.

The window is a rolling offset from each run's date, not a fixed calendar date. This matters for scheduled watchers: a fixed date would give a shrinking window run after run until the question stopped being meaningful, so the ask is re-anchored every time the watcher runs.

Central answers from two signals. Your own delivery record supplies the order-state half. The other half is synthesized centrally: for each SKU it probes the watched counterparty and the interchangeable trading-pair vendors reachable from it, reducing each response to available, partial or unavailable. The result is a SKU-to-vendor report rather than the flat signal grid a conventional watcher produces.

A watcher requesting the soft-quoted signal with no asks is valid, and the console says so plainly rather than treating it as a misconfiguration: it simply cannot answer a readiness question, because none was asked. Lead-time history shows the quantity each run actually asked for, not the template's current ask projected backwards; the "current ask" line in the header is template state and is labelled as such.

8.4Grounded Forecasting

Grounded forecasting answers a question the other monitoring modes cannot: what can the network actually deliver for a product that does not exist yet?

You name the new product, nominate one to three existing products as analogues, edit a bill of materials seeded from the primary analogue, enter your final assembly time and set a monthly demand profile. A run simulates the production history the product would generate, probes the network per component through phantom demand to derive current lead times from quoted timelines, pulls your own observed delivery history as aggregates, and computes the critical path per component class:

last_commit(class, month) = delivery_date − assembly_days − lead_days(class)

The classes with the earliest last-commit dates are the pacers: the components that decide whether the schedule is achievable at all.

The primary output is a commitment schedule, a standalone plain-text artifact written for the brand you supply. It leads with the pacers and carries evidence inline for each: current quoted lead time, the observed minimum and maximum from your own history, and a confidence level. It exists to be handed to a customer as the basis for asking them to commit financially to a projection, so it is deliberately readable on its own without console access.

Two caveats. The forecast is grounded in analogues, so answer quality follows the products you nominate; a poorly chosen analogue produces a confident number about the wrong supply chain. And lead times come from live probes, so a run reflects the network on the day it ran, not a standing guarantee.

Your agent needs no new configuration. It answers the phantom-demand probes it already answers and supplies delivery-history aggregates through two MCP tools.

What actually happens is fixed: quote delivery retries exactly once, on a 5xx only, after waiting backoff_base_s; execution delivery retries exactly once and immediately; max_retries and backoff_max_s are unread on both paths. Beyond that single retry, an undelivered quote request is queued for replay when your agent returns (§7.5). Do not size your endpoint's availability budget around a retry count that is not applied.

10.4OAuth2 / Keycloak Authentication

All haiCore calls use a Keycloak client_credentials bearer token. Use TokenManager from @haiwave/client-sdk — it caches and refreshes for you. The reference implementation is network/token-manager.ts.

10.6Chat Conformance Invariants

If your agent offers the conversational surface, it must preserve these six invariants (enforced behaviorally by the conformance kit in §10.7):

  1. Full intent taxonomy. Route against the complete VALID_INTENTS set (36 intents: order, quote, catalog, gofish, inventory, pricing, specs, resolution, audit, and the eleven seller-side native-quote intents of §7.8) — no narrowing of the taxonomy; unknown intents fall back to general.
  2. Write-confirmation gate. No write executes without explicit user acknowledgment (the pending-confirmation state machine).
  3. Grant ACL with a quote_accept → quote_owner_outbound floor. No lowering. The four grants are reviewer, the two scoped quote_owner_* siblings, and owner (§6.10) — not a hierarchy. Each user carries a roles array and must declare at least one; a users file still carrying the retired single role field refuses to load, and the error names the replacement for each old value.
  4. The 13 transaction-touching chains at their prescribed payloads and call sequences: orderConfirmChain, quoteRequestChain, quoteAcceptChain, quoteAttachPoChain, quoteStatusChain, quoteCompareChain, orderLookupChain, gofishQueryChain, catalogSearchChain, productResolutionChain, sourceAuditChain, manifestStatusChain, vendorQuoteStartChain.
  5. Eight pipeline phases in order: guardTurn → handlePendingConfirmation → detectContextFilter → prepareRouterInput → routeAndRemapIntents → executeSubIntents → saveSearchContext → finalizeTurn — with the scope, haiwave_only, and write-confirmation gates unconditional.
  6. WebSocket message shape { type, content_panel, intent }.

Everything else — which LLM, which local-data backend, UI, auth provider — is unconstrained. The executable companion to these invariants is the conformance kit (§10.7), which pins both Tier 0 and Tier 1 behaviorally.

Two further prescribed contracts, outside chat. (1) receive_catalog_query must refuse a query with no search term: text that is empty or only whitespace is rejected with an empty_query error alongside the existing validation refusal (v1.67). It is a guard rather than a nicety: an empty query used to return an arbitrary slice of the catalog, which is disclosure nobody asked for. (2) The envelope quote status is derived from the lines by the rule in §7.1d (complete / partial / unable). The conformance kit exercises both.

Baseline Deployment Environments

The Quick Start assumes one thing about your infrastructure: Docker on a host, with the volumes and network access it describes. This appendix is for teams standing up that host fresh. It gives a vetted baseline for four target environments and the trade-offs between them, so the environment decision does not stall the first hour. If you already run a container platform with persistent block storage, you likely need none of this; deploy as you normally would and honor the requirements in A.1.

A.1Requirements Common to Every Environment

These follow from the agent's architecture (§4.1) and apply regardless of where the container runs:

  • Compute. 2 vCPU / 4 GB RAM minimum; the embedding model and DuckDB run in-process. 4 vCPU / 8 GB is comfortable for larger catalogs and document libraries.
  • Persistent block storage, not network file systems. A durable volume for /data, starting around 20 GB (it grows with catalog, documents, and chat log). DuckDB is a single-writer embedded file: NFS, SMB, and object-storage mounts (EFS, Azure Files, GCS FUSE) are unsupported for the data volume. Use encrypted block storage; DuckDB is not encrypted at rest.
  • Exactly one replica. The agent does not scale horizontally: one database file, one writer, one network identity. Run one container instance and size it vertically.
  • Always on. No scale-to-zero. A sleeping agent fails its inbound dispatches and is shown unreachable to its owner until it answers again (§4.3).
  • Outbound HTTPS to HAIWAVE Central, Keycloak, your model provider, and (first boot only) the embedding model repository.
  • Inbound. HAIWAVE Central must reach /mcp at the address you advertise in AGENT_PUBLIC_URL, over HTTPS. Restrict the chat UI to your team's network; it shares port 3001 with the MCP endpoint, so the restriction lives in your proxy or firewall rules, not the agent.
  • TLS and secrets. Terminate TLS in a proxy or load balancer in front of the agent, and inject credentials from a secret manager at start. Never bake secrets into the image.

A.3Local / On-prem Docker (the Quick Start default)

This is the environment the Quick Start assumes; the steps below harden it from evaluation to something you can leave running.

  1. Docker Engine 24+ on a 64-bit glibc host (the image is Debian-based, §4.1). 2 vCPU / 4 GB minimum.
  2. Use the named volumes exactly as in the Quick Start, on encrypted storage.
  3. Put a reverse proxy (nginx, Caddy) in front of localhost:3001 for TLS, and set AGENT_PUBLIC_URL to the external HTTPS address. Restrict /chat to your internal network in the proxy.
  4. Add --restart unless-stopped to the run command so the agent survives host reboots.
  5. Back up the data volume on a schedule. DuckDB is a single file; stop the container (or snapshot the volume) for a consistent copy.

Trade-offs. Simplest path and full control; patching, backups, monitoring, and availability are entirely yours. The right choice for evaluation, air-gapped-adjacent environments, and teams that already operate their own hosts.

A.4AWS: EC2 with an EBS Data Volume

The assured AWS baseline is a single EC2 instance running the Quick Start unchanged. ECS on Fargate is not recommended: its persistence option is EFS, which is NFS, and unsupported for the DuckDB data volume (A.1). If your organization mandates ECS, use the EC2 launch type with an EBS-backed host volume and a single task.

  1. Launch a t3.medium (or m6i.large for headroom) with an encrypted gp3 EBS volume attached and mounted at /data-vol. Install Docker.
  2. Store the Quick Start credentials in Secrets Manager or SSM Parameter Store; render agent.env from them at instance start (user data or your config-management tool).
  3. Run the Quick Start command, replacing the named volumes with bind mounts onto the EBS mount: -v /data-vol/config:/data/config -v /data-vol/data:/data.
  4. Put an Application Load Balancer with an ACM certificate in front of instance port 3001; set AGENT_PUBLIC_URL to the ALB's HTTPS address.
  5. Security groups: inbound 443 on the ALB restricted to HAIWAVE Central's published source range (34.106.85.228/32, §6.7) plus your corporate egress for /chat; instance inbound only from the ALB.
  6. Snapshot the EBS volume on a schedule (Data Lifecycle Manager) for backups.

Trade-offs. Managed TLS and load balancing with minimal moving parts; instance patching is still yours (SSM Patch Manager covers it). Costs are dominated by the instance; the agent idles lightly between queries.

A.5Azure: VM with a Managed Disk

Same shape as AWS. Container Instances and Container Apps persist to Azure Files, which is SMB, and unsupported for the data volume (A.1); a small VM is the assured baseline.

  1. Create a Standard_B2ms (or D2s_v5) VM with an encrypted managed data disk mounted at /data-vol. Install Docker.
  2. Store credentials in Key Vault; render agent.env at start (cloud-init or your config-management tool).
  3. Run the Quick Start command with bind mounts onto the disk: -v /data-vol/config:/data/config -v /data-vol/data:/data.
  4. Put Application Gateway (with a managed certificate) in front of port 3001; set AGENT_PUBLIC_URL accordingly.
  5. NSG rules: inbound 443 restricted to HAIWAVE Central's published source range (34.106.85.228/32, §6.7) plus your corporate egress for /chat; VM inbound only from the gateway.
  6. Schedule disk snapshots (Azure Backup) for the data volume.

Trade-offs. Equivalent posture to the AWS baseline. Choose it because your estate is on Azure, not for any agent-specific reason; the agent is indifferent.

A.6GCP: Compute Engine, with a Cloud Run Example

The assured GCP baseline is Compute Engine: an e2-medium (or larger) VM with an encrypted persistent disk at /data-vol, Docker, Secret Manager for credentials, and an external HTTPS load balancer in front of port 3001. The steps mirror A.4 one-for-one with GCP's equivalents.

Cloud Run is an evaluation-only example, not an assured environment. It conflicts with two A.1 requirements: its file system is ephemeral (DuckDB state does not survive an instance replacement, and its durable mount options are GCS FUSE and Filestore, both unsupported for the data volume) and it wants to scale to zero, which the network's availability expectations forbid (a scaled-to-zero agent fails its inbound dispatches). Pinned to a single always-on instance it can host the agent for a short evaluation:

gcloud run deploy haiwave-agent \
  --image <your-registry>/haiwave-agent \
  --cpu 2 --memory 4Gi --port 3001 \
  --min-instances 1 --max-instances 1 --no-cpu-throttling \
  --set-secrets "ANTHROPIC_API_KEY=anthropic-key:latest,KEYCLOAK_CLIENT_SECRET=kc-secret:latest" \
  --set-env-vars "PARTICIPANT_ID=…,AGENT_ID=…,DUCKDB_PATH=/tmp/agent.duckdb"

Set AGENT_PUBLIC_URL to the service's run.app HTTPS address (Cloud Run provides TLS). Expect the catalog, documents, and chat state to reset whenever the instance is replaced; that is acceptable for a first-hour walkthrough of the Quick Start and for nothing else. Move to Compute Engine before seeding real data.

Rule of thumb. If a platform cannot give the container a private, durable block device and a process that never sleeps, it can demo the agent but should not deploy it.
